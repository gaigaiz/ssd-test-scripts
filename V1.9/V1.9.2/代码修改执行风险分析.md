## 2. 详细风险分析

### R-01: NVMe Format --ses=1 执行失败或设备不支持

**风险描述**：
`nvme format /dev/nvme0n1 --namespace-id=1 --ses=1` 命令要求SSD控制器支持User Data Erase。部分企业级SSD或旧固件可能不支持SES=1，导致命令返回错误。

**影响**：
- FOB状态无法通过NVMe Format进入
- 自动回退到blkdiscard，但blkdiscard仅发TRIM，不等同于真正的FOB

**缓解措施**：
1. 代码已实现自动回退：`--purge-method=auto`（默认）时，NVMe Format失败后自动回退blkdiscard
2. 可通过 `--purge-method=user-data` 强制仅使用NVMe Format，失败则报错
3. 可通过 `--purge-method=blkdiscard` 强制仅使用blkdiscard
4. 日志中明确记录实际使用的擦除方式

**验证方式**：
```bash
# 检查设备是否支持User Data Erase
sudo nvme id-ctrl /dev/nvme0 | grep -i "ses\|format"
# 测试执行
sudo nvme format /dev/nvme0n1 --namespace-id=1 --ses=1
```

### R-02: WDPC稳态检测耗时过长

**风险描述**：
WDPC每轮包含3个跟踪变量测试，每个测试点默认60秒。最多25轮，理论最大耗时：
- 25轮 × 3变量 × 60秒 = 4500秒 = 75分钟
- 加上WIPC顺序写2遍（约10-30分钟，取决于容量和速度）
- 总耗时可能达到 **1.5-2小时**

**影响**：
- 稳态预处理时间显著增加（v1.9.1固定方案约30-60分钟）
- 测试效率降低

**缓解措施**：
1. 可通过 `--steady-point-duration` 缩短每个测试点时长（如30秒）
2. 可通过 `--steady-max-rounds` 减少最大轮数（如15轮）
3. 达到稳态后立即停止，不一定跑满25轮
4. 日志中实时输出每轮稳态检测结果

**参数建议**：
| 场景 | max_rounds | point_duration | 预计耗时 |
|-----|-----------|---------------|---------|
| 快速验证 | 10 | 30 | ~15分钟 |
| 标准测试 | 25 | 60 | ~45-75分钟 |
| 严格规范 | 25 | 60 | ~45-75分钟 |

### R-03: 状态文件读写冲突或损坏

**风险描述**：
状态文件 `~/.ssd_test_state.json` 可能在以下情况损坏：
- 多个进程同时写入
- 写入过程中程序崩溃
- 磁盘空间不足

**影响**：
- GUI显示错误的SSD状态
- 状态一致性校验逻辑判断错误

**缓解措施**：
1. 代码使用临时文件+`os.replace()`原子写入，避免半写状态
2. 读取失败时默认返回Unknown状态，不中断主流程
3. 写入失败时仅打印警告，不中断主流程
4. 状态按设备序列号隔离，多设备测试互不影响

**状态文件位置**：`~/.ssd_test_state.json`

**手动修复**：
```bash
# 查看状态文件
cat ~/.ssd_test_state.json
# 重置状态（删除文件后重启GUI）
rm ~/.ssd_test_state.json
```

### R-04: GUI subprocess调用脚本路径错误

**风险描述**：
GUI的`build_command()`和状态切换方法中，脚本路径硬编码为 `~/max_tool/ssd_test_v1.9.2.py`。如果脚本未放置在该路径，GUI启动测试时会报"文件不存在"错误。

**影响**：
- GUI无法启动任何测试
- 手动状态切换功能失效

**缓解措施**：
1. 必须将脚本放置在 `~/max_tool/ssd_test_v1.9.2.py`
2. 启动前验证脚本存在：`ls -la ~/max_tool/ssd_test_v1.9.2.py`
3. 如路径不同，需修改代码中两处脚本路径引用

**代码中的脚本路径引用**：
- `build_command()` 方法：`script_path = os.path.expanduser("~/max_tool/ssd_test_v1.9.2.py")`
- `_enter_ssd_state()` 方法：同上
- `_enter_ssd_state_and_test()` 方法：同上

### R-05: 三分支状态逻辑判断错误

**风险描述**：
开始测试时的三分支逻辑可能出现以下错误：
- 状态文件读取失败导致误判为Unknown
- perf_state=both时目标状态判定错误
- 状态不一致时用户选择"是"但状态切换失败

**影响**：
- 重复进入FOB/稳态（浪费时间）
- 跳过状态进入直接测试（测试结果不可比）
- 状态切换失败后仍尝试测试

**缓解措施**：
1. 状态读取失败时默认Unknown，走分支A直接测试
2. perf_state=both时目标状态固定为FOB（先执行FOB测试）
3. 自动进入状态后校验返回码，失败则取消测试
4. 日志中明确记录每个分支的判断结果

**三分支逻辑说明**：
| 当前状态 | 目标状态 | 行为 |
|---------|---------|------|
| Unknown | 任意 | 直接测试，不进入任何状态 |
| FOB | FOB | 直接测试，不重复进入 |
| Steady | Steady | 直接测试，不重复进入 |
| FOB | Steady | 警告弹窗，用户选择自动进入或取消 |
| Steady | FOB | 警告弹窗，用户选择自动进入或取消 |

### R-06: SMART忽视5353逻辑误判

**风险描述**：
性能测试中的SMART健康检查会忽视介质错误ID 5353。但如果：
- nvme error-log输出格式与预期不同
- 错误ID字段名不匹配
- 5353之外的错误被误判为5353

**影响**：
- 真正的介质错误被忽视，导致带病测试
- 或5353错误未被正确忽视，导致测试中断

**缓解措施**：
1. 仅在性能测试中使用此SMART检查（其他测试类不受影响）
2. 错误日志读取失败时按计数器>0警告（保守策略）
3. 可通过 `--smart-ignore-media-errors` 参数修改忽视的错误ID列表
4. SMART检查失败不中断性能测试（仅警告）

**注意**：PerformanceTester类中目前未在run()主流程中调用`_check_smart_health()`，该方法为预留接口。如需启用，需在run()方法中手动添加调用。

### R-07: 稳态检测算法参数与SNIA规范偏差

**风险描述**：
本次实现的稳态检测算法基于SNIA SSS PTS v2.0.2规范，但可能存在以下偏差：
- 跟踪变量的块大小/队列深度/读写比例与规范不完全一致
- 测试点数量（规范要求56个点/轮，本次仅3个跟踪变量）
- 稳态判定阈值（Range≤20%，Slope≤10%）已按规范实现

**影响**：
- 稳态判定结果可能与官方认证测试有差异
- 不适合作为正式认证依据，仅用于内部研发测试

**缓解措施**：
1. 3个跟踪变量覆盖了随机写、混合读写、随机读三种典型场景
2. 稳态判定阈值严格按规范实现（5轮滑动窗口、Range≤20%×Ave、Slope≤10%×Ave）
3. 文档中明确说明为"SNIA规范近似实现"，非官方认证工具
4. 如需完整规范测试，建议使用官方SNIA PTS测试工具

### R-08: 其他7个测试类受间接影响

**风险描述**：
本次修改主要集中在PerformanceTester类和GUI，但新增的全局函数（状态管理）和TestConfig字段可能间接影响其他测试类。

**影响**：
- 其他测试类初始化TestConfig时可能因新增字段报错
- 全局函数名冲突

**缓解措施**：
1. TestConfig新增字段均有默认值，不影响其他测试类初始化
2. 新增全局函数（load_ssd_state/save_ssd_state/get_device_serial）使用独特命名，无冲突
3. 其他7个测试类代码未做任何修改
4. 语法检查已通过

**其他测试类清单**（均未修改）：
- FirmwareTester（固件升降级）
- SmartTester（SMART健康信息）
- CapacityTester（容量测试）
- ReadWriteTester（读/写测试）
- PowerCycleTester（电源循环）
- SPORTester（意外电源循环）
- OSInterruptionTester（操作系统中断）
- TestReport（报告生成）

### R-09: Python版本兼容性问题

**风险描述**：
目标环境为Python 3.10.12，代码中使用的语法和库需兼容该版本。

**影响**：
- 语法错误导致脚本无法运行
- 库函数行为差异

**缓解措施**：
1. 未使用Python 3.11+专属语法（如match-case、ExceptionGroup等）
2. dataclasses、argparse、subprocess等均为3.10标准库
3. tkinter为GUI标准库，Ubuntu 22.04默认安装
4. 已通过py_compile语法检查

**可能需要安装的系统包**：
```bash
sudo apt install python3-tk  # tkinter GUI支持
```

### R-10: sudo权限不足导致nvme format失败

**风险描述**：
`nvme format`命令需要root权限。如果通过普通用户权限运行GUI，即使使用pkexec提权，也可能因sudoers配置或polkit策略导致失败。

**影响**：
- FOB状态进入失败
- 自动回退到blkdiscard

**缓解措施**：
1. 建议使用 `sudo python3 ~/max_tool/ssd_test_v1.9.2.py --gui` 启动GUI
2. GUI中已实现pkexec提权提示，但nvme format可能需要更严格的权限
3. 命令行模式必须使用sudo运行
4. 日志中明确记录权限相关错误

**推荐启动方式**：
```bash
sudo python3 ~/max_tool/ssd_test_v1.9.2.py --gui
```

## 5. 已知限制

1. **SMART健康检查未启用**：`_check_smart_health()`方法已实现但未在PerformanceTester.run()主流程中调用，如需启用需手动添加。
2. **稳态检测为简化实现**：仅使用3个跟踪变量，非SNIA规范要求的56个测试点/轮。
3. **状态持久化依赖文件**：状态文件损坏或删除后状态重置为Unknown。
4. **GUI状态切换为异步操作**：点击按钮后通过subprocess执行，期间GUI界面可能短暂无响应。
5. **不支持Windows**：所有操作（nvme format、blkdiscard、fio等）均为Linux命令。
