# 脚本使用步骤 — 读/写测试 (Read/Write Test)

> 基于 `ssd_test_v1.8.5.py` 脚本，对应 DVT Test Plan 中 **Data Read&Write Test**（Table 7）与 EVT 中 **Read and Write Test**（Table 12）测试项。

---

## 一、测试目的

验证 SSD 数据读写功能正常，数据完整性无丢失/损坏/比特错误：

- SSD 能够正常读取和写入数据
- 读写过程中无数据错误、设备无法被系统识别等异常
- **Pass Condition**：数据写入 SSD 后再从设备读取，内容完全正确

对应文档要求：
- **DVT — Data Read&Write Test**（Table 7）：ASUS B560M + i5，PCIe 4.0，Windows 10，Passmark BurnIn Tool，4 pcs
- **EVT — Read and Write Test**（Table 12）：Gigabyte X570 + AMD Ryzen 7 5700G，PCIe 4.0，Windows 10，Passmark Burn-in 10.0，1 pcs

## 二、测试环境要求

| 项目 | 要求 |
|------|------|
| 测试平台 | x86_64 PC |
| Host Controller | PCIe 4.0 / NVMe 1.4 |
| 操作系统 | Linux（Ubuntu / CentOS Stream 等，脚本原生支持） |
| 待测 SSD | 安装为**次级驱动器**（非系统盘），设备路径如 `/dev/nvme1n1` |
| 权限 | **必须 root**（`sudo` 运行） |
| 依赖工具 | `nvme-cli`, `smartmontools`, `fio`, `util-linux` |

### 依赖安装（Ubuntu/Debian）

```bash
sudo apt update
sudo apt install -y nvme-cli smartmontools fio util-linux
```

## 三、工具说明

| 文档工具 | 脚本替代工具 | 用途 |
|----------|-------------|------|
| Passmark BurnIn / Burn-in 10.0 | **fio** | 持续读写 I/O 负载 + 数据完整性校验 |
| 数据校验（BurnIn 内置） | **fio verify** | 写入时计算校验和（md5/sha256/crc32），读取时自动比对 |

脚本使用 fio 的 `--verify` 机制：写入时在每个 block 头部存储校验和，读取验证阶段自动逐块比对，发现不一致立即报错并 dump 错误块。

### v1.8.5 新增：多 job 并发验证（offset_increment）

v1.8.5 之前，verify 模式下 `numjobs>1` 会导致多个 job 从 offset 0 开始写入同一区域，互相覆盖，fio 会输出警告且验证不可靠。

v1.8.5 引入 **`--offset_increment`** 机制，让每个 job 写入独立的物理区域：

```
Job 1: offset 0        → size 区域
Job 2: offset size     → size 区域
Job 3: offset 2×size   → size 区域
Job 4: offset 3×size   → size 区域
```

各 job 互不干扰，verify 正常工作，同时保留高并发写入压力。

**容量保护**：当 `文件大小 × numjobs > 设备容量` 时，脚本自动降级 numjobs 并输出 WARNING，不会越界写入。

## 四、三种测试模式

脚本提供三种测试模式，可单独执行或全部执行（`--rw-mode all`）：

### 模式 1：full_disk — 全磁盘写入 + 读取验证

对整个 SSD 裸设备执行：
1. **阶段1**：全磁盘顺序写入（fio write，numjobs=用户配置，带 verify 校验和，不立即验证）
2. 检查设备是否仍在线（写入后不掉盘）
3. **阶段2**：全磁盘顺序读取验证（fio read，**numjobs=1**，do_verify=1，逐块校验）
4. 最终设备在线检查

> 全磁盘读取验证使用单 job 顺序读取，确保 verify pattern 一致性（全磁盘不适用 offset_increment）。写入阶段仍保留用户配置的高并发 numjobs。
>
> 适合验证全盘数据保持能力，耗时较长（1TB 盘约 30-60 分钟）。

### 模式 2：file_cycle — 多文件大小重复读写周期

对选定的文件大小（256MB / 1GB / 4GB / 16GB / 32GB），每个大小执行指定次数的**写+读验证**循环：
- 单次 fio 完成写入后立即读取验证（do_verify=1）
- **支持多 job 并发**：通过 `--offset_increment` 让每个 job 写独立区域
- 超过设备容量的文件大小自动跳过
- `文件大小 × numjobs > 设备容量` 时自动降级 numjobs
- 全部完成后执行 SMART 健康检查

> 适合验证不同数据量下的读写稳定性，模拟典型文件操作场景。

### 模式 3：long_run — 长期读写验证

1. **准备**：写入前 32GB 基准数据（带 verify 校验和）
2. **运行**：持续 N 小时（默认 24h）混合读写负载（randrw，70% 读 / 30% 写，time_based，numjobs=用户配置）
3. **验证**：读取前 32GB 基准数据并验证完整性（**支持多 job 并发**，`--offset_increment=32G`）
4. 最终设备在线检查 + SMART 健康检查

> 适合长期稳定性验证，模拟真实使用场景下的持续读写压力。可媲美 PassMark BurnInTest 的长时间连续读写测试。

## 五、命令行模式使用步骤

### 5.1 快速验证（仅全磁盘模式，小参数）

```bash
cd /path/to/script
sudo python3 ssd_test_v1.8.5.py \
  -d /dev/nvme1n1 \
  -t rw \
  --rw-mode full_disk \
  --rw-block-size 128k \
  --rw-iodepth 32 \
  --rw-verify md5 \
  -y
```

### 5.2 标准测试（三种模式全部执行）

```bash
sudo python3 ssd_test_v1.8.5.py \
  -d /dev/nvme1n1 \
  -t rw \
  --rw-mode all \
  --rw-file-sizes 256MB 1GB 4GB 16GB 32GB \
  --rw-cycles 3 \
  --rw-pattern random \
  --rw-verify md5 \
  --rw-long-hours 24 \
  --rw-block-size 4k \
  --rw-iodepth 32 \
  --rw-numjobs 4 \
  --rw-mixed-read-ratio 70 \
  -y
```

### 5.3 仅多文件周期模式（快速功能验证）

```bash
sudo python3 ssd_test_v1.8.5.py \
  -d /dev/nvme1n1 \
  -t rw \
  --rw-mode file_cycle \
  --rw-file-sizes 256MB 1GB 4GB \
  --rw-cycles 2 \
  --rw-verify md5 \
  --rw-numjobs 4 \
  -y
```

### 5.4 仅长期运行模式（缩短为 2 小时验证）

```bash
sudo python3 ssd_test_v1.8.5.py \
  -d /dev/nvme1n1 \
  -t rw \
  --rw-mode long_run \
  --rw-long-hours 2 \
  --rw-block-size 4k \
  --rw-iodepth 32 \
  --rw-numjobs 4 \
  --rw-mixed-read-ratio 70 \
  -y
```

### 5.5 Dry-Run 试运行

```bash
sudo python3 ssd_test_v1.8.5.py -d /dev/nvme1n1 -t rw --dry-run
```

### 9.2 SMART 检查行为（v1.8.3 起调整）

| 检查项 | 阈值 | 行为 |
|--------|------|------|
| 介质错误 (media_errors) | > 0 | **WARNING**（仅警告，不判 FAIL，已知历史问题） |
| 可用备件 (available_spare) | < 10% | **FAIL**（寿命预警，硬性指标） |
| 温度 | < 0°C 或 > 70°C | **FAIL**（温度异常，硬性指标） |

> 介质错误为已知历史问题时，脚本仅输出 WARNING 并继续测试。如果测试中介质错误数持续增长，需关注 SSD 健康状态。

### 9.3 失败判定

| 失败场景 | 判定 |
|---------|------|
| fio verify 检测到数据不一致 | FAIL（fio 会输出错误块的 offset 和 expected/actual 值） |
| 写入或读取过程中设备掉盘 | FAIL（设备节点不存在） |
| SMART 可用备件 < 10% | FAIL（寿命预警） |
| SMART 温度异常（<0°C 或 >70°C） | FAIL（过热/过冷） |
| fio 命令执行异常/超时 | FAIL 或 ERROR |

> **注意**：SMART 介质错误 > 0 不再判 FAIL（v1.8.3 起改为 WARNING）。

### 9.4 JSON 报告

报告文件保存在 `./reports/ssd_test_report_*.json`，读/写测试部分包含：
- `测试模式`：执行的模式
- `子项结果`：各模式的详细结果和带宽数据
- `失败详情`：如有失败，记录失败原因

## 十、注意事项与常见问题

### ⚠️ 安全注意

1. **确认设备路径**：`-d` 参数务必指向待测 SSD，**绝不能指向系统盘**（测试直接对裸设备写入，会破坏所有数据）
2. **数据备份**：测试会对待测盘执行全盘写入，执行前务必备份
3. **必须 root**：裸设备写入需要 root 权限
4. **全磁盘模式耗时较长**：1TB SSD 全盘写入+读取约需 30-60 分钟，2TB 约 1-2 小时，请耐心等待
5. **长期运行模式**：默认 24 小时，建议使用 `nohup` 或 `tmux` 后台运行，避免 SSH 断开导致测试中断

### numjobs 配置建议（v1.8.5 新增）

v1.8.5 起 verify 模式支持多 job 并发，通过 `--offset_increment` 隔离各 job 的写入区域。配置时注意：

- **容量要求**：`文件大小 × numjobs ≤ 设备容量`。超出时脚本自动降级 numjobs 并输出 WARNING。
- **推荐配置**：`iodepth=32, numjobs=4`（总队列深度 128），适合高性能 NVMe SSD。
- **低性能设备**：可降低为 `iodepth=16, numjobs=2`，避免 CPU 成为瓶颈。
- **file_cycle 大文件**：选择 32GB 文件大小时，`numjobs=4` 需要 128GB 空间，512GB 盘没问题；如果是 256GB 盘且选了 32GB，numjobs=4 需要 128GB 也可以，但 numjobs=8 就会被降级。

### 常见问题

**Q: fio verify 报错 "verification failed" 怎么办？**
A: 这表示读取到的数据与写入时的校验和不一致，说明 SSD 存在数据保持问题。检查日志中的错误块 offset，确认是否集中在特定 LBA 范围。可以更换 `--rw-pattern`（如 0xAA / 0x55）重新测试，排除随机数据偶发问题。

**Q: 日志中出现 "fio: multiple writers may overwrite blocks" 警告？**
A: v1.8.5 已通过 `--offset_increment` 解决此问题，多 job 写入独立区域不会互相覆盖。如果仍看到此警告，说明 fio 版本较旧不支持 offset_increment，或设备容量不足导致 numjobs 被降级。脚本会自动提取 JSON 部分，警告行不影响解析。

**Q: 全磁盘模式可以只测一部分吗？**
A: 全磁盘模式会对整个裸设备写入。如果只想测部分容量，使用 `file_cycle` 模式并选择较大的文件大小（如 32GB），或使用性能测试模块。

**Q: 长期运行模式可以中途停止吗？**
A: 可以按 `Ctrl+C` 终止 fio 进程。但终止后基准数据验证不会执行，测试结果为不完整。建议让测试自然完成。

**Q: 测试中设备掉盘了怎么办？**
A: 脚本会检测设备在线状态，掉盘后立即记录 FAIL 并终止当前模式。检查：①SSD 散热是否正常（过热可能导致掉盘）；②PCIe 插槽接触是否良好；③电源供电是否充足；④查看 `dmesg` 内核日志确认掉盘原因。

**Q: md5 / sha256 / crc32 校验方式有什么区别？**
A: 检测能力：sha256 > md5 > crc32；性能开销：sha256 > md5 > crc32。默认 md5 在检测能力和性能之间取得平衡。对数据完整性要求极高时可选 sha256。

**Q: SMART 介质错误警告会影响测试结果吗？**
A: 不会。v1.8.3 起介质错误 > 0 仅输出 WARNING，不判 FAIL，测试会继续执行。只有可用备件 < 10% 或温度异常才会判 FAIL。如果介质错误数在测试过程中持续增长，需关注 SSD 健康状态。

**Q: GUI 底部看不到日志摘要怎么办？**
A: v1.8.5 已修复此问题。底部日志摘要区固定 6 行高度，始终可见。如果窗口太小，可拖动窗口边缘放大，或调整左侧测试项列表宽度。

## 十一、快速命令参考

```bash
# 1. 快速功能验证（仅 file_cycle，3个大小，每大小2轮，numjobs=4）
sudo python3 ssd_test_v1.8.5.py -d /dev/nvme1n1 -t rw \
  --rw-mode file_cycle --rw-file-sizes 256MB 1GB 4GB \
  --rw-cycles 2 --rw-verify md5 --rw-numjobs 4 -y

# 2. 全磁盘数据完整性验证
sudo python3 ssd_test_v1.8.5.py -d /dev/nvme1n1 -t rw \
  --rw-mode full_disk --rw-block-size 128k \
  --rw-iodepth 32 --rw-verify md5 -y

# 3. 完整测试（三种模式全部执行，长期24h，numjobs=4）
sudo python3 ssd_test_v1.8.5.py -d /dev/nvme1n1 -t rw \
  --rw-mode all --rw-cycles 3 --rw-long-hours 24 \
  --rw-verify md5 --rw-block-size 4k --rw-numjobs 4 -y

# 4. 短期长期运行验证（2小时）
sudo python3 ssd_test_v1.8.5.py -d /dev/nvme1n1 -t rw \
  --rw-mode long_run --rw-long-hours 2 --rw-numjobs 4 -y

# 5. 指定 pattern 测试（0xAA 棋盘格，更容易发现位翻转）
sudo python3 ssd_test_v1.8.5.py -d /dev/nvme1n1 -t rw \
  --rw-mode file_cycle --rw-pattern 0xAA --rw-verify sha256 -y

# 6. 高并发压力测试（numjobs=8，注意容量要求）
sudo python3 ssd_test_v1.8.5.py -d /dev/nvme1n1 -t rw \
  --rw-mode file_cycle --rw-file-sizes 256MB \
  --rw-cycles 5 --rw-numjobs 8 --rw-iodepth 64 -y

# 7. 试运行（不实际写入）
sudo python3 ssd_test_v1.8.5.py -d /dev/nvme1n1 -t rw --dry-run

# 8. 后台运行长期测试（防止 SSH 断开）
nohup sudo python3 ssd_test_v1.8.5.py -d /dev/nvme1n1 -t rw \
  --rw-mode long_run --rw-long-hours 24 -y > rw_long_run.log 2>&1 &
```
